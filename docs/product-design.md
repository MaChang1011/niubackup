# 多用户备份产品设计

- 日期：2026-10-31
- 基线：方案二单用户版（M1 协议与接收端已验证、M2 安卓端已入网验证）
- 定位升级（2026-10-31 定版）：从自用工具升级为**对外多用户产品**——开放注册、数据隔离全部正规化
- 硬性要求：**文件备份必须支持断点续传**（见 §5.3）
- 修订（2026-10-31 二版，他定版）：①备份与回传**只走打洞直连（p2p），永不走中继**（见 §5.5）；②服务端不保存任何文件，只保存**文件级备份记录**；③手机端可查看备份记录、可经直连隧道下载与在线播放 PC 上的副本；④App 内逐文件标注备份状态，**已备份完成的文件可删除本地原件**释放空间（见 §6）
- 修订（2026-10-31 三版，他定版）：①**文件级备份记录改存 PC 端**，服务端只保存账号、组网、授权与日志（计数级，无文件名与哈希）；手机端的「已备份」凭证改为 PC 签发的完成回执、本地保存（见 §5.1、§6.2、§7.1）；②**缩略图/封面由 PC 端在文件落盘时生成**（图片缩略图、视频封面帧），手机浏览「仅 PC 有」文件时经直连按需加载（见 §7.1）
- 修订（2026-10-31 四版）：组网隔离定版为「**一个共享公共节点 + 每用户独立组网（一户一网）**」——公共节点不加入任何用户网络、只做发现与打洞协调，跨用户在组网层即互不可达，一期即如此（不再列为后期演进，见 §4 第 3 层）
- 修订（2026-10-31 五版，他定版）：**取消授权期限**——产品现为开源免费，注册即永久授权：无试用期、无到期拦截、无续费概念；账号停用、设备吊销、设备数量上限保留不变（见 §3.3）

## 1. 产品定位

面向普通用户的「手机照片/文件自动备份到自家 PC」工具：

- 用户在自家 PC 装接收端、在安卓手机装客户端，两边登录同一账号即自动组网备份
- **备份数据只存在用户自己的 PC 上，平台不经手、不存储文件内容**——这是隐私卖点，也是合规减压点：平台只存账号、设备、授权和备份状态等元数据
- 平台侧提供：账号与授权、设备配对、组网 rendezvous、状态汇总、管理后台
- 传输策略定版：**打洞直连成功才传文件，永不经服务器中继**——服务器零文件流量、零中继带宽；直连打不通时备份等待（见 §5.5）
- 闭环体验：备份完成后手机可经直连隧道把文件取回或在线播放，确认已备份的文件可删本地原件释放手机空间（「释放空间」式体验）

## 2. 总体架构（控制面 / 数据面分离）

```
安卓客户端 ──登录/领配置/上报状态──▶ 账户服务（控制面，云服务器）
    │                                   ▲
    │ 备份流量（组网直连，不经平台）        │ 登录/同步授权/上报状态
    ▼                                   │
PC 接收端 ──────────────────────────────┘
组网 rendezvous 节点（云服务器）：一个共享公共节点（不加入任何用户的网络），为所有用户各自独立的组网做发现与打洞协调；不转发用户文件（产品策略直连-only，见 §5.5）
管理后台（Web）：与账户服务同体部署，管理员使用
```

- **数据面**：手机 → EasyTier 组网 → 用户自己的 PC。点对点加密传输，平台不参与；**仅 p2p 直连时传输，中继路径不传文件**（§5.5）。PC 接收端同时是文件服务端：向机主手机提供已备份文件的清单、下载（同样支持断点续传）与在线播放（ ranged 流式读取）
- **控制面**：注册登录、设备绑定与批准、令牌发放与吊销、授权（设备上限/配额，无期限）、组网配置下发、会话日志汇总（仅计数：时间/文件数/字节数/结果，**无文件名、无哈希**）。**文件级备份记录只保存在用户 PC 本地**（§7.1），服务端不保存
- 技术选型：账户服务与管理后台用 Spring Boot + PostgreSQL（部署在他现有云服务器）；PC 接收端与安卓端沿用已验证的 Java/Kotlin + EasyTier JNI 代码

## 3. 账号、设备与授权

### 3.1 账号
- 注册：邮箱或手机号 + 密码（密码以 Argon2/bcrypt 哈希存储，平台永不存明文）
- 登录：账号密码 → 换取访问令牌（短期）+ 刷新令牌；支持踢下线（改密/后台停用即失效）

### 3.2 设备
- 每台手机、每台 PC 是一个 device，归属一个账号；设备有独立的设备令牌（可单独吊销）
- 配对流程：PC 端登录后显示「待批准设备」；手机登录同一账号后，PC 端点批准，配对成立。未批准的设备令牌不能备份
- 设备上限（默认：手机 2 台 + PC 1 台，可在后台调整）

### 3.3 授权（License）
- 字段：生效时间、设备数上限、单设备容量配额、功能开关；`expires_at` 统一写远未来哨兵值（9999-12-31），表示无到期
- **无授权期限（2026-10-31 五版定版）**：产品开源免费，注册即永久授权——无试用期、无到期停止会话、无续费概念；账户服务的校验接口不再返回 `license_expired`，接收端也不再有到期门禁；后台续期接口保留但为无操作（兼容旧调用，仍写审计）
- 保留的管控（与期限无关，不受本次取消影响）：账号停用（停用即拒绝登录与新会话）、设备吊销（即时生效）、设备数量上限
- 状态校验：客户端/接收端登录时向账户服务校验设备身份与状态并缓存令牌哈希，离线时凭缓存放行已批准设备（离线宽限，避免平台短暂不可用导致用户备份中断）

## 4. 数据隔离（三层）

1. **归属隔离（主）**：每台 PC 接收端登录机主账号后，**只接受绑定在同一账号下、且已被批准的手机设备**。A 用户的手机连上 B 用户的 PC，也会被拒绝
2. **协议隔离**：备份协议 v2 的 HELLO 必须携带 user_id + device_id + 设备令牌；接收端验令牌（本地缓存的令牌哈希清单，由账户服务同步）后，才允许进入该用户专属目录 `users/<userId>/devices/<deviceId>/`，路径越界直接拒绝
3. **组网层（一户一网，一期即如此）**：云服务器只跑**一个共享公共节点**——它以共享模式运行，**不加入任何用户的网络**，只为所有网络做节点发现与打洞协调。每个用户注册时由账户服务生成**自己独立的组网**（独立 network_name + secret），他的手机与 PC 只进自己的网。EasyTier 以网络身份做隔离：**不同网络在公共节点上互不可见、互不可达，公共节点不会跨网转发一个字节**；即使发生中继转发，流量也是以该用户网络密钥端到端加密的，节点运营方（我们）看不到内容，只能看到连接元数据。某个用户的 secret 泄露只影响他自己，吊销=轮换他一人的 secret，不波及他人。一台服务器承载的网络数量以千计时发现流量仍极小（打洞协调是小包），现有云服务器足够。注：自用的 machang-net 与产品公共节点同机、不同实例、不同端口，互不干扰

传输加密：EasyTier 隧道本身加密；文件在用户 PC 上以明文原样保存（用户自己的磁盘，产品不做二次加密，避免恢复门槛）。

## 5. 备份协议 v2

### 5.1 会话流程（沿 v1 骨架升级）
1. `HELLO {version:2, user_id, device_id, device_token}` → 接收端校验身份、授权、配对状态，失败返回明确错误码（未授权/未批准/令牌无效）；且双方的 peer 路由必须为 p2p 直连（见 §5.5），不满足则会话不启动、不报错、转入等待
2. 客户端发送**增量清单**（见 5.2）→ 接收端逐文件回复决策：跳过 / 发送 / **续传偏移量**
3. 逐文件传输（停等式，沿 v1）→ 接收端写 `.part`、终检、原子改名（见 5.3）
4. `RECEIPT {ok, skipped, failed}` → 双方记账；**接收端在每个文件终检通过后即写入本地记录库**（相对路径、大小、SHA-256、完成时间，见 §7.1），并向手机签发**完成回执**（含文件清单与哈希、由 PC 设备密钥签名），手机本地保存为「已备份」凭证；上报服务端的只有会话汇总日志（计数级，无文件名）

### 5.2 增量清单与哈希缓存（解决 306 GB 全量重算问题）
- 客户端本地维护清单缓存：`path + size + mtime → sha256`。文件未变（size+mtime 一致）直接复用旧哈希，不重算
- 清单只包含「新增/变更」文件与全量索引摘要；接收端按 size+mtime+sha 三重比对决定跳过
- 首次全量哈希仍不可避免（306 GB 约需十几分钟），但**只发生一次**，且可断点（缓存随算随存，中断重启不重来）

### 5.3 断点续传（硬性要求，本节为验收标准）

**目标：任何中断（断网、App 被杀、手机重启、PC 重启、组网切换）后，已传部分不丢，下次会话从断点继续，绝不整文件重传。**

- **偏移协商**：清单决策阶段，接收端对每个待收文件检查本地 `<目标路径>.part` 的现有长度 L，向客户端回复「从偏移 L 开始发送」；客户端 seek 到 L 处续传。`.part` 与目标文件同目录同卷，保证最终改名是原子操作
- **跨会话/跨重启持久**：`.part` 文件即进度本身，不依赖内存状态；接收端重启后按 `.part` 长度自然恢复进度。客户端侧在清单缓存中记录在途文件，重启后优先续传未完成项
- **完整性终检**：文件传完后接收端计算整文件 SHA-256 与清单哈希比对，一致才把 `.part` 原子改名为正式文件并恢复 mtime；不一致则丢弃 `.part` 并在回执中标记该文件失败（下次会话整文件重传——这是唯一允许整文件重传的情形）
- **源文件变更失效**：若源文件在两次会话之间 size 或 mtime 变了，旧 `.part` 作废（删除后从 0 开始），避免把两个版本的文件拼在一起
- **大文件分块（v2.1 增强）**：超过 256 MB 的文件按 8 MB 分块、逐块校验记录进度，续传粒度细化到块级，坏块只补该块，不必整文件终检失败后全量重来（一期先上偏移续传，分块紧随其后）
- **进度可见**：客户端与 PC 端都显示「已传/总量、当前文件、当前文件内偏移」，后台状态汇总含最近一次会话的完成度
- **验收用例**（M4a 必须全过）：①传一个 2 GB 视频，50% 时杀掉手机 App，重启后从 50% 续传且终检通过；②50% 时重启 PC 接收端，同上；③50% 时关闭组网再打开，同上；④续传前修改源文件，旧进度作废且不产生拼凑文件

### 5.4 重试与退避
- 连接失败/中断：客户端指数退避重试（1s→60s 封顶），充电+WiFi 条件下自动重试；连续失败只记状态不打扰用户
- 接收端对同一设备的并发会话只允许一个，其余排队/拒绝并回执说明

### 5.5 直连门槛（产品定版策略：不走中继）

**规则：备份、下载、播放三类文件传输，只在打洞成功、隧道为 p2p 直连时进行；经服务器中继（relay）的路径一律不传文件。** 服务端由此保持零文件流量、零中继带宽，且用户数据永不经第三方机器。

- **判定**：会话开始前，手机与 PC 各自查本地 EasyTier 的 peer 路由状态（cost=p2p / relay）；HELLO 中互告判定结果，双方都确认直连才进入清单阶段。传输中途若直连掉为中继，立即暂停（已传部分按 §5.3 保留），等直连恢复后续传
- **等待状态机**：`待备份 → 等待直连（持续打洞重试，退避 1 分钟封顶）→ 直连建立 → 传输中 → 完成`。自动备份的触发条件因此变为四条：充电 + WiFi + 空闲 + **直连可达**
- **用户可见**：App 与 PC 端明确显示「等待直连」状态与原因（对方不在线 / 正在打洞 / 当前网络难以打通），并提供「立即尝试打洞」按钮，不让用户对着不动的进度条猜
- **已知代价（接受为产品政策）**：双方都是对称型 NAT 等极端组合可能长期打不通，这类用户会一直处于等待直连——这是为零中继成本与隐私付的价，定版接受；是否留「付费中继」后门列入 §12 待决，默认不做

## 6. 安卓端

- 登录页（注册/登录/找回密码）→ 登录后自动领取组网配置与设备令牌，**不再手动粘密钥**
- 备份范围：一期 DCIM（照片/视频），后续开放自选文件夹
- 调度：充电时 + WiFi + 设备空闲三者齐备才自动备份；手动「立即备份」不受限制
- 前台服务与 VPN：沿 M2 已修复的形态（权限声明齐全、TUN 建立后再提升前台服务）；与用户自有代理 App 的单 VPN 位冲突要在 UI 明示
- 状态：本地展示最近备份结果；向上报汇总到账户服务（仅元数据）
- 令牌存 Android Keystore；卸载重装视为新设备重新批准

### 6.1 文件库与备份状态标注
- App 内置文件库视图（一期即 DCIM 网格/列表），**每个文件带状态徽标**：未备份 / 备份中（含进度）/ 已备份 / 仅 PC 有（本地已删）
- 状态来源：本地索引（扫描+哈希缓存）+ 手机保存的 PC 完成回执（「已备份」的离线凭证）+ 直连上 PC 时与 PC 记录库实时对账，三者合并展示

### 6.2 备份记录查看
- 记录本体在 PC（§7.1）：「备份记录」页在直连上 PC 时实时读取 PC 记录库——文件名、大小、备份完成时间、完整性状态、缩略图（§7.1）；PC 不可达时展示手机本地缓存的最近一份记录与回执，并标注「记录截至 HH:MM」
- 服务端不存文件记录，记录页的数据来自 PC 或手机缓存——服务端宕机不影响用户查自己的备份

### 6.3 下载与在线播放（经直连隧道从 PC 取回）
- 前提同 §5.5：隧道直连且 PC 在线；不满足时按钮置灰并说明原因
- 下载：协议 v2 增加反向通道（清单查询 / 按偏移读取），**下载同样支持断点续传**，下回本地后状态徽标恢复为「已备份（本地+PC）」
- 播放：视频/音频走 ranged 流式读取，边下边播不落整文件；播放缓存不计入本地副本状态

### 6.4 删除本地文件（释放空间）
- **可删条件**：手机存有该文件的 PC 完成回执（终检通过凭证）；PC 当前可达时再实时核对副本完整性状态，异常则锁定不可删
- 流程：单文件或批量「释放空间」→ 二次确认（明示将删数量与可释放容量、PC 副本位置；PC 不可达时额外提示「未做实时核对，依据备份时的完成回执」）→ 删除本地原件 → 徽标变「仅 PC 有」
- 安全边界：无回执的文件永不出现在可删列表；误删兜底靠 §6.3 随时取回

## 7. PC 接收端

- 登录机主账号；系统托盘常驻、开机自启；主窗口含：存储目录设置、配额、待批准设备、已绑定设备、备份记录、日志
- 存储布局：`users/<userId>/devices/<deviceId>/<相对路径>`，与协议层目录一致
- 打包：**Windows / Linux / macOS 三平台同为一等公民**（2026-10-31 定版）：jpackage 在各目标系统上分别构建、捆绑运行时与各平台原生工具（easytier-core、ffmpeg 等），普通用户双击安装；细节见 §14.2
- 本地安全：接收端只监听组网地址，不监听公网/局域网地址
- 文件服务：接收端维护本地备份索引，对机主手机（同一套设备令牌校验、仅直连时）提供清单查询、按偏移下载与 ranged 流式播放读取
- 完整性自检：接收端定期（如每日空闲时）抽查/全量校验已备份文件与记录库哈希是否一致，结果记入本地记录库、手机连接时读取展示——这是手机端敢删本地原件的信任来源；自检异常的文件在手机端自动锁定删除并提示用户

### 7.1 PC 本地记录库与缩略图（封面）

- **记录库**：接收端本地 SQLite，表 `files`（相对路径、大小、SHA-256、备份完成时间、来源设备、完整性状态、缩略图指针）。这是全产品**唯一**的文件级记录存放地；服务端、管理后台都看不到文件名与哈希
- **回执签名**：PC 持设备密钥对，会话完成回执（文件清单+哈希）签名后交手机保存；服务端只负责在配对时登记 PC 公钥，手机据此验回执真伪，防伪造「已备份」
- **缩略图/封面（需要，且在 PC 生成）**：文件终检落盘后由 PC 生成——图片生成长边 320px 缩略图，视频抽取封面帧（ffmpeg），存入记录库旁的 thumbs 目录。理由：PC 有原件、算力与电源，不耗手机电量、不经服务端；手机备份时**不**额外传缩略图
- **手机侧使用**：浏览「仅 PC 有」/备份记录时，经直连按需拉取缩略图并在手机本地缓存（LRU）；PC 不可达时先显示文件名+类型图标占位，连上后自动补齐。这样本地已删的文件在手机上依然「看得见脸」，敢删、好找、能取回
- **例外**：PC 无法解码的格式（如部分 RAW/HEIC 变体）缩略图生成失败 → 回退类型图标；后续可加「手机备份时顺带生成缩略图上传 PC」作补充手段（列入 M4c 评估，不进一期必做）

## 8. 账户服务与管理后台

数据表（核心）：`users`（账号、密码哈希、状态）、`devices`（归属、类型、令牌哈希、批准状态、最后在线、PC 公钥）、`licenses`（配额、设备上限；无到期）、`session_logs`（会话与登录日志：设备、时间、文件数、字节数、结果——**计数级，无文件名、无哈希**）、`admin_audit`（后台操作留痕）。**服务端只保存账号、组网、授权与日志；不保存任何文件内容，也不保存文件级备份记录**（记录在 PC 本地，见 §7.1）

后台功能：用户列表/搜索、开通、停用/恢复、设备管理（解绑、吊销令牌）、全局备份状态总览、异常设备提醒（续期接口保留为无操作，见 §3.3）

部署：云服务器 + PostgreSQL（复用现有实例）；**上线前置：域名 + HTTPS 证书**（客户端只走 HTTPS 调控制面），若面向大陆公众运营另需完成 ICP 备案等手续，列入上线检查单

## 9. 安全与隐私原则

- 平台留存最小化：不存文件内容、不存文件名、不存文件哈希；服务端只有账号、授权、组网信息与计数级日志，文件级记录全程只在用户自己的 PC 与手机之间
- 密码 Argon2/bcrypt；令牌只存哈希；控制面全程 HTTPS；后台强制强密码 + 操作审计
- 客户端日志默认只存本机，用户主动反馈时才上传

## 13. 技术调研结论（2026-10-31）

调研方式：官方文档（easytier.cn、developer.android.com、Oracle 文档）+ 开源源码实证（EasyTier 主线源码在笔记本 ~/src/EasyTier）+ 现网实测。凡与原假设有出入处均标注 ⚠️ 并已修正设计。

### 13.1 公共节点与多网络隔离 —— 成立，且有一个默认行为要收紧
- 共享节点有两种官方形态：①**裸启动**（easytier-core 不带任何参数：不设网络名/密钥、无虚拟 IP、不需要 root），纯做公共节点，不加入任何网络；②一个跑着自己网络的普通节点也可同时充当公共节点。我们采用形态①，与自用节点彻底分开
- 客户端以 `-p tcp://<公共节点>:11010` 接入并带自己的 network_name/secret；路由同步只发生在同名同密钥的网络内，多网络共用一个节点互不可见（官方快速组网指南 + README）。主线源码的回归测试亦实证：未知凭据节点经共享节点接入时会被目标网络的路由域拒绝
- ⚠️ **默认中继过于开放**：EasyTier 节点**默认替任意网络中继**。产品公共节点必须加 `--relay-network-whitelist`（按网络名通配，只放行产品网络命名空间）或 `--private-mode`，否则等于免费替全网跑中继、吃带宽。（附带发现：我们现网自用的服务器节点同样在默认中继状态，建议单独收紧，见文末备注）
- 结论：§4 的「一个共享节点 + 一户一网」成立，公共节点按裸启动 + 白名单部署

### 13.2 组网加密与安全模式 —— 定版启用 Secure Mode
- 默认加密开（AES-GCM），但 legacy 模式的密钥由 network_secret 派生、全网共享：**密钥一旦泄露，全网流量可被解密**；且同网成员理论上能解同网的中继流量。裸公共节点不是成员、不知密钥，只转发密文
- **Secure Mode**（`--secure-mode`）：Noise 协议、每节点独立 X25519 密钥对、逐对协商——官方原文：即使流量经第三方共享节点/公共中继，中继也无法解密。客户端还需固定公共节点的公钥（peer_public_key）防冒名
- **定版**：产品所有客户端（手机/PC）启用 secure mode；账户服务下发配置时一并下发公共节点公钥。手机与自家 PC 是同网仅有的成员，legacy 风险本就低，secure mode 把中继与密钥泄露两条线一并封死

### 13.3 直连判定 —— 读路由 cost，不用自研探测
- peer 路由信息含 cost（1=直连 p2p，≥2=经中继；现网实测见过 p2p 与 relay(2) 两种显示），经 JNI 的 collectNetworkInfos 可在 App 内读取，PC 侧同理。§5.5 的门槛实现 = 会话前双方各查到对方的路由 cost==1 才开传，中途 cost 变化即暂停

### 13.4 回执签名算法 —— 定版 ECDSA P-256
- ECDSA P-256（SHA256withECDSA）在 Android 平台 API 11+ 即支持、Keystore 基线能力，minSdk 26 无忧；Java 侧（PC）标准库原生支持
- Ed25519 在 Android Keystore 要 API 33+ 且硬件支持不普遍 —— **否决**。PC 记录库的回执签名统一 ECDSA P-256，公钥在配对时登记到服务端（§8 devices 表已含公钥字段）

### 13.5 在线播放 —— Media3 自定义 DataSource，成立
- Media3/ExoPlayer 的 DataSource 契约本身是按位置随机读（open 时带 position/length），播放器会按任意偏移 open —— 与我们协议的 ranged 读取天然对齐：实现一个把协议 READ 请求喂给播放器的 DataSource 即可边下边播，无需本地文件、无需在 PC 上另开 HTTP 服务
- 注意点：MP4 若 moov atom 在文件尾，播放器会先跳尾读取 —— 协议 READ 必须支持任意偏移（我们的断点续传偏移机制正好复用），首播延迟取决于一次尾部往返，可接受

### 13.6 缩略图管线 —— 分工定版
- 图片（JPEG/PNG 等）：PC 端纯 Java 解码缩放（ImageIO 基线格式足够）
- ⚠️ **HEIC**：Java ImageIO 不支持（read 直接返回 null）；ffmpeg 对手机 HEIC 的分块网格图（tile grid）合成不可靠 —— 定版用 **ImageMagick + libheif（含 libde265 插件）** 作 HEIC 解码器，随 PC 安装包按平台捆绑；再失败才回退类型图标
- 视频封面：捆绑的 ffmpeg 抽帧（前 10 秒内取首个非黑帧、缩到 320 宽），成熟做法
- 三平台的原生工具（easytier-core、ffmpeg、magick）均有官方 Win/Linux/macOS 构建，按平台打包分发即可

### 13.7 设备令牌 —— 不用 JWT，用不透明令牌 + 哈希存储
- 需逐设备可吊销的场景，JWT 的自包含特性反而碍事（签发后到期前无法 centrally 作废，除非再叠一层服务端状态）。定版：每设备一个高熵随机令牌，服务端只存其哈希 + 签发/到期/吊销标志，校验走查库；吊销 = 改一行，即时生效。账户服务的少量接口规模下查库开销可忽略

### 13.8 调研结论汇总
| 原假设 | 结论 | 设计影响 |
|---|---|---|
| 一个公共节点服务多网且隔离 | ✅ 成立（裸启动形态 + 源码测试实证） | §4 定版不变 |
| 节点默认不替别人中继 | ⚠️ 相反：默认全网中继 | 公共节点加白名单；自用节点建议收紧 |
| 中继看不到内容 | ✅ 但 legacy 模式密钥泄露=全网可解 | 全员 secure mode（13.2） |
| cost 可判定直连 | ✅ | §5.5 按 cost==1 实现 |
| Ed25519 做回执签名 | ❌ 安卓 33+ 才有 | 改 ECDSA P-256 |
| 播放需在 PC 开 HTTP 服务 | 不需要 | 播放器 DataSource 直读协议 |
| ffmpeg 通吃缩略图 | ⚠️ HEIC 不可靠 | HEIC 交 ImageMagick+libheif |
| JWT 做设备令牌 | 不合适 | 不透明令牌 + 哈希存储 |

## 14. 架构设计（2026-10-31）

### 14.1 总体视图

```
┌─ 安卓客户端 ─────────────┐        ┌─ 云服务器 ──────────────────┐
│ UI(文件库/记录/设置)      │ HTTPS  │ 账户服务(Spring Boot)        │
│ 备份引擎(扫描/哈希缓存)   │───────▶│  ├ 账号/设备/授权/令牌/日志  │
│ 组网桥(EasyTier JNI)     │  控制面 │  └ 管理后台(Web)             │
│ 媒体(DataSource/播放器)  │        │ 公共节点(easytier-core 裸启动 │
│ 本地存储(索引/回执/缓存)  │        │  + relay 白名单, 不入任何网)  │
└──────────┬───────────────┘        └──────────────────────────────┘
           │  数据面: 本用户组网内直连(p2p, secure mode)
┌──────────▼───────────────┐
│ PC 接收端(Win/Linux/mac) │
│ 接收引擎(协议 v2 服务端)  │
│ 文件服务(清单/下载/播放)  │
│ 记录库(SQLite)+缩略图管线 │
│ 完整性自检               │
│ easytier-core 子进程     │
└──────────────────────────┘
```
分层原则：控制面（服务端）只碰身份与授权；数据面（组网直连）只在用户自己的设备之间；记录面（PC 本地）只存用户自己的文件记录。三面互不越界。

### 14.2 PC 端架构 —— Windows / Linux / macOS 三平台

- **一份 Java 代码三平台共用**：接收引擎、文件服务、记录库、自检、缩略图调度全部纯 Java（JDK 21）；平台差异只收敛在三个薄适配点：
  1. **组网进程**：easytier-core 以子进程（sidecar）方式由主程序拉起/守护，捆绑对应 OS/架构的官方二进制（win-x64、linux-x64/arm64、mac-x64/arm64）；主程序不做 JNI，升级组网版本=换二进制
  2. **系统集成**：托盘用 Java SystemTray（macOS 菜单栏图标走同一 API）；开机自启分别走 Windows 注册表 Run/任务计划、Linux systemd user unit、macOS LaunchAgent，由安装后首次运行按 OS 注册
  3. **原生工具**：ffmpeg、ImageMagick(+libheif) 按平台捆绑进安装包（体积约 +60~90 MB，可接受；备选为首启按需下载，列 M4c 评估）
- **本地存储**：sqlite-jdbc 单文件库（记录库，§7.1）；文件本体按 `users/<userId>/devices/<deviceId>/` 落盘；缩略图存 `.thumbs/` 旁路目录，不污染用户文件树
- **打包流水线**：jpackage 必须在目标系统上构建 —— 用 GitHub Actions 三个 runner（windows/macos/ubuntu）并行出包：Windows exe 安装包（需 WiX）、macOS dmg、Linux deb/AppImage；版本号与更新通道统一，自动更新只提示不强推
- **进程守护**：主进程崩溃自拉起（各 OS 服务机制）；easytier-core 子进程由主程序看门狗重启；PC 重启后全链路自恢复，用户无感

### 14.3 安卓端架构

模块（在 M2 已验证骨架上演进）：`ui`（登录/文件库/记录/设置）→ `engine`（扫描、哈希缓存、会话状态机含 §5.5 直连等待）→ `mesh`（EasyTier JNI 桥，配置由账户服务下发，含 secure mode 与公共节点公钥）→ `media`（Media3 + 自定义 DataSource 走协议 ranged 读）→ `store`（本地索引 SQLite、完成回执、缩略图 LRU 缓存、Keystore 令牌）。前台服务与 VPN 沿 M2 已修复形态。

### 14.4 服务端架构

- **账户服务**：Spring Boot 单体（他的老本行，好维护）：REST 接口分四组——auth（注册/登录/刷新）、devices（登记/批准/吊销、PC 公钥登记）、license（查询/校验）、admin（后台页 + 操作审计）。PostgreSQL 存 §8 的表；令牌为不透明随机串、库存哈希（§13.7）
- **公共节点**：独立 easytier-core 进程，裸启动 + `--relay-network-whitelist` 只放行产品网络名前缀 + 固定密钥对供客户端 secure mode 固定公钥；与账户服务同机不同进程，互不依赖（节点挂了不影响登录，后台挂了不影响已配对设备的组网发现之外的功能——备份的直连判定与传输不经账户服务）
- **入口**：nginx 反代 + HTTPS（域名/证书为上线前置）；管理后台仅管理员账号 + 强密码 + 审计

### 14.5 核心时序

**注册与配对**：手机注册→服务端建号并发永久授权（无到期）+生成本用户组网（name/secret）→手机与 PC 分别登录、登记设备（PC 生成 ECDSA 密钥对、公钥登记）→PC 端批准手机设备→双端拉取各自组网配置（含公共节点地址与公钥）→入网待命。
**一次备份**：触发条件满足（充电/WiFi/空闲）→双端查路由 cost，==1 才继续（否则等待状态机）→HELLO 验令牌与设备状态→增量清单（哈希缓存）→逐文件：偏移协商→传输→终检→写记录库+生成缩略图→会话回执签名交手机→服务端只记一条计数日志。
**浏览与取回**：手机直连 PC→读记录库+缩略图→点播走 DataSource ranged 读、下载走偏移续传→落回本地后徽标更新。
**删本地**：校验手机存有该文件签名回执（+PC 可达时核对自检状态）→二次确认→删除→徽标「仅 PC 有」。

### 14.6 数据模型（要点）

- PC SQLite `files`：path、size、sha256、mtime、device_id、backed_at、integrity（ok/suspect/missing）、thumb（相对路径可空）；`sessions`：本地会话流水
- 服务端 PG：`users`、`devices`（含 pc_pubkey）、`licenses`、`session_logs`（计数级）、`admin_audit` —— 与 §8 一致，**无任何文件级表**

### 14.7 协议 v2 消息表（在 v1 线格式上扩展，JSON 行 + 二进制体）

| 消息 | 方向 | 用途 |
|---|---|---|
| HELLO / HELLO_ACK | 手机→PC | 身份（user/device/令牌哈希校验）、授权、双方 cost 声明 |
| MANIFEST | 手机→PC | 增量清单（path/size/mtime/sha256） |
| DECIDE | PC→手机 | 逐文件：skip / send@offset（续传起点） |
| DATA / FILE_END | 手机→PC | 文件体（自 offset 起）/ 单文件结束触发终检 |
| RECEIPT | PC→手机 | 签名完成回执（ECDSA P-256） |
| LIST / READ / THUMB | 手机→PC | 记录库查询 / 按偏移读（下载与播放共用）/ 缩略图拉取 |
| REPORT | 双端→服务端 | 仅计数级会话日志（HTTPS，非组网内） |

### 14.8 部署拓扑与非功能

- 一期单机部署（现有云服务器）：账户服务 + PG（复用现有实例的独立库）+ 公共节点 + nginx；全部 systemd 守护；备份对象只有 PG 的账号库（小 volume，每日导出）
- 可用性：公共节点与账户服务解耦部署，单点故障只影响新注册/新配对，不影响已配对用户的发现与备份（发现依赖公共节点——其故障会使新直连建立变难，已有直连不受影响；多节点列 M5）
- 安全清单（上线前逐项核）：公共节点白名单生效、secure mode 全员开启、后台强密码+审计、HTTPS、令牌哈希存储、PC 只监听组网地址、安装包签名（Win/macOS 证书列入成本项，M4c 前决策）
