# EasyTier 自动备份 App — 方案二设计（2026-10-30 定）

## 决策背景
- 方案一（Syncthing-Fork + EasyTier 现成组合验证一周）于 2026-10-30 放弃：手机端 APK 被 ColorOS 安装器拦截（报 "APK damaged"），分发摩擦过大；改走方案二半自研。
- 组网现成：machang-net（10.200.0.0/24），笔记本 10.200.0.2、手机 10.200.0.3、公司台式机 10.200.0.4、服务器 10.200.0.1。

## 总体架构（三个组件）
1. **PC 接收端（自研，Java）**：跑在笔记本上，监听组网地址，接收备份、按设备/目录落盘、维护已备份清单。选 Java 的原因：MaChang 的老本行，后续他能自己维护迭代。笔记本现状：有 OpenJDK 25 JRE，缺 javac，M1 部署时补装 JDK 或在本机编译后拷 jar。
2. **同步协议（自研，刻意做小）**：一条 TCP 长连接完成一次备份会话：
   - 握手：设备名 + 协议版本；
   - 清单交换：发送端给出文件列表（相对路径、大小、mtime、SHA-256），接收端回哪些需要传、每个从哪个偏移续传；
   - 传输：逐文件流式发送，接收端写临时文件，校验哈希通过后原子改名落盘；
   - 结束：接收端回执（成功/失败清单）。
   信任边界：v1 以组网成员身份为信任基础（私有网络 + 网络密钥），协议内只做设备名标识；应用层令牌放 M3 硬化。
3. **Android 客户端（自研，内嵌 EasyTier）**：Kotlin + easytier-android-jni，App 自己加入组网（不再依赖单独的 EasyTier App 切换），监听 DCIM 变化，后台增量推送到接收端。iOS 本轮不做。

## 里程碑
- **M1 接收端 + 协议骨架**：Java 接收端 + 测试发送端，先在 PC 之间（台式机 → 笔记本，走组网 10.200.0.2）跑通端到端：清单比对、增量跳过、断点续传、哈希校验、落盘目录结构。
- **M2 Android 客户端**：内嵌组网打通（能 ping 通接收端）、手动触发一次 DCIM 全量备份、再做后台自动增量。
- **M3 硬化**：应用层令牌、省电调度（充电/WiFi 条件）、多目录选择、失败重试与通知、接收端托盘/服务化。

## v1 默认范围（如需改口，一句话即可）
- 接收端装在**家里笔记本**（常开、容量大），目标目录沿用 `~/PhoneBackup`。
- 备份内容 v1 只做**照片/视频（DCIM）**，跑通后再扩到任意目录。
- 手机不在家时经组网直连备份（EasyTier 由 App 内嵌，不与代理抢 VPN 槽位的问题在 M2 实测验证）。

## 已知风险（来自前期调研）
- iOS 后台限制与国内 App Store 分发：本轮不碰 iOS。
- LGPL-3.0：EasyTier 内嵌需动态链接 + 署名 + 源码提供义务，M2 打包时落实。
- Android 后台保活因厂商而异（尤其 ColorOS）：M2 要在 MaChang 自己的手机上实测触发积极性与耗电。
